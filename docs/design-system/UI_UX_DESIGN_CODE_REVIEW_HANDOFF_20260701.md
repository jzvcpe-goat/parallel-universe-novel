## Product UX Principles

1. Reader and Creator are separate products.
   Reader screens should prioritize reading, requests, voting, and update status. Creator screens should prioritize request handling, writing, local drafts, publish review, work management, and writing preferences.

2. Creator is author-first.
   The first useful question is always: "What should the author write, decide, or publish next?" The UI should not lead with system status, database state, or implementation vocabulary.

3. Agent assistance must be visible through authoring affordances.
   The assistant is not a chat decoration. It must provide executable writing actions, local shortcuts, generated candidates, adoption plans, impact review, and author-controlled confirmation.

4. Candidate adoption is controlled by the author.
   Generated text stays in a candidate state until the author applies it. Candidate cards must show how adoption works before any action button.

5. No engineering residue in product UI.
   Public product copy must not expose implementation terms such as provider, fallback, trace, API key, backend, database, RLS, Supabase, sync, or prompt plumbing.
